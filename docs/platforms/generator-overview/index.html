Targets and What They Support

Cloudhopper deploys the same annotated functions to six targets. Each target is a generator (it writes handler classes, Terraform and API descriptions at compile time) plus a provider (the runtime library the generated handlers call). You pick the target with a Maven profile:

Profile / generator IDTargetGenerator moduleProvider module
aws-terraformAWS Lambdagenerator-aws-terraformprovider-aws
azure-terraformAzure Functionsgenerator-azure-terraformprovider-azure
gcp-terraformGoogle Cloud Functions (2nd gen)generator-gcp-terraformprovider-gcp
springboot-httpSpring Boot service on any servergenerator-springbootprovider-springboot, provider-http
knativeKnative service on Kubernetes (Helm chart)generator-knativeprovider-springboot, provider-http
scaleway-terraformScaleway Serverless Containersgenerator-scaleway-terraformprovider-springboot, provider-http

All modules are listed in Modules.

Support matrix​

Every generator declares which annotations and attributes it supports. The same declarations drive the build and the compatibility tests (TCK): when you compile for a target, the build warns about every annotation or attribute it does not claim (see When a target does not support something), and the TCK certifies each target against the tests whose features it claims. Notes on the event and trigger columns:

  • @EventTrigger lists the event sources a target supports as rows below source; today every target supports QUEUE and STORAGE. On Spring Boot it is the endpoint POST /events/<function name>, and queues can also be consumed from Kafka (see Queues from Kafka). On Knative a queue is a Kafka topic; storage events have no generated source and are posted to POST /events/<function name> like on Spring Boot. On Scaleway a queue is a Scaleway Queue (SQS); storage events have no trigger there either.
  • A function without a trigger can be invoked directly on AWS (Lambda invoke). On Azure every function also gets the HTTP route /api/<function name>_http_function_trigger, and on GCP every function has an HTTPS URL. On Spring Boot, Knative and Scaleway every function gets the endpoint GET/POST /functions/<function name>; set cloudhopper.functions.direct-endpoint=false to switch these off.
  • Vendor-specific settings, such as the processor architecture on AWS, go through @Extension and are only read by the target they are meant for.

What each target generates​

Every target has its own page with the generated files, the Terraform variables or Helm values, how schedules and queues are delivered, how messages are sent, and the runtime modules it needs:

  • AWS Lambda
  • Azure Functions
  • Google Cloud Functions
  • Spring Boot
  • Knative
  • Scaleway Serverless Containers

Configuration​

Functions read configuration from environment variables; each target passes them its own way.

TargetHow to set values
aws-terraform, gcp-terraformTerraform variable cloudhopper_config; each function gets the values of the properties it reads
azure-terraform, scaleway-terraformTerraform variable cloudhopper_config; all functions run in one app or container and get all values
knativeHelm value env (list of name/value)
springboot-httpenvironment variables or system properties (-Dreport.bucket=…) of the process

cloudhopper_config is a map from property name to value, for example in a .tfvars file:

cloudhopper_config = {
  "report.bucket" = "acme-reports-prod"
  "report.days"   = "30"
}

On AWS and GCP, terraform plan fails if a function reads a property without defaultValue that neither the map nor your own Terraform sets, and names the missing properties. Values are plain environment variables of the function: keep secrets out of them.

Secrets​

Secrets are referenced, not copied:

TargetHow to reference secrets
aws-terraformTerraform variable cloudhopper_secrets, property name to the ARN or name of a Secrets Manager secret; see AWS
knativeHelm value secrets: property name, Kubernetes secret and key; see Knative
scaleway-terraformTerraform variable cloudhopper_secrets, property name to the value, passed as a secret environment variable; the value is stored in the Terraform state; see Scaleway
springboot-httpenvironment variables or system properties of the process, set from the secret store of the platform
azure-terraformTerraform variable cloudhopper_secrets, property name to the resource ID of a Key Vault secret; see Azure
gcp-terraformTerraform variable cloudhopper_secrets, property name to a Secret Manager secret; see GCP

On Spring Boot, @ConfigProperty reads MicroProfile Config, not Spring's application.properties; set the values as environment variables or system properties.

Values from your own Terraform​

The generated files and your own .tf files form one Terraform module, and a variable cannot refer to resources or data sources of its own module. Values that your Terraform creates or reads, such as the client ID of a user pool created next to the functions or a parameter read with a data source, go into two locals instead. The generated files declare them empty; redefine them in an override file, a file named override.tf or <name>_override.tf in src/main/resources/deployment/<target>/:

# cloudhopper_override.tf
locals {
  cloudhopper_extra_config = {
    "auth.issuer"    = "https://${aws_cognito_user_pool.main.endpoint}"
    "auth.client-id" = aws_cognito_user_pool_client.main.id
  }
  cloudhopper_extra_secrets = {
    "report.api-key" = aws_secretsmanager_secret.report_key.arn
  }
}
  • cloudhopper_extra_config adds values to cloudhopper_config, cloudhopper_extra_secrets adds references to cloudhopper_secrets, in the same format: aws_secretsmanager_secret.<name>.arn on AWS, azurerm_key_vault_secret.<name>.resource_versionless_id on Azure, google_secret_manager_secret.<name>.secret_id on GCP, the value on Scaleway.
  • A property may be set only once in the two variables and the two locals; terraform plan fails and names the properties that are set more than once.
  • Terraform creates the referenced resources before the functions that read them, in the same terraform apply.
  • Knative and Spring Boot take their configuration from Helm values and the environment and are not affected.

Terraform and provider versions​

The generated Terraform requires Terraform >= 1.5.0, < 2.0.0 (required_version) and is tested with Terraform 1.17.

Terraform allows only one required_providers block per directory. The provider versions therefore belong in your own main.tf, next to the provider configuration. The exception is Scaleway, where the generated files declare the provider. Projects created with the archetype already contain these constraints:

TargetProvider constraints in main.tf
aws-terraformhashicorp/aws ~> 6.0
azure-terraformhashicorp/azurerm ~> 4.0
gcp-terraformhashicorp/google ~> 8.0, hashicorp/google-beta ~> 8.0, hashicorp/local ~> 2.0
scaleway-terraformnone: the generated files declare scaleway/scaleway ~> 2.92. Do not add a required_providers block to your main.tf

Without a constraint, terraform init installs the latest major version of the provider, which the generated files may not support. Older projects should add the block, for example on AWS:

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

Maven configuration​

Projects created with the archetype have a profile per target, so building for a target is mvn clean install -P<generator ID>. Each profile adds the generator (in provided scope: only the annotation processor uses it) and the provider (the runtime of the generated handlers), and passes the generator ID to the annotation processor:

<compilerArgs>
    <arg>-AgeneratorId=${generator.id}</arg>
    <arg>-AconfigOutputDir=${project.build.directory}/deployment/${generator.id}</arg>
    <arg>-AartifactId=${project.artifactId}</arg>
    <arg>-Aversion=${project.version}</arg>
    <arg>-Aclassifier=${jar.classifier}</arg>
    <arg>-AtargetDir=${project.build.directory}</arg>
</compilerArgs>

Writing Functions

With Cloudhopper you write plain Java methods and describe them with a few annotations. You never implement a cloud-specific interface: the annotation processor reads your annotations at compile time and generates the provider-specific handler and deployment artifacts for you.

A function is just a method annotated with @Function plus a trigger:

public class HelloFunction {

    @Function(name = "hello")
    @HttpTrigger(method = "GET", path = "/hello/{name}",
                 summary = "Say Hello", description = "Returns a friendly greeting")
    public String handleRequest(@PathParam String name) {
        return "hello " + name;
    }
}

@Function​

Marks a method as a deployable function and carries provider-neutral deployment metadata. Only name is required.

Which target applies which attribute is listed in the support matrix.

AttributeTypeDefaultDescription
nameString—Unique function name in the deployment target
memoryint128Memory limit in MB
timeoutint30Maximum run time in seconds
minInstancesint0Instances kept warm to reduce cold starts; not applied by any target yet (#26)
extensions@Extension[]{}Vendor-specific attributes (see Vendor extensions)
@Function(name = "resize", memory = 512, timeout = 60)

Triggers​

Trigger annotations decide how a function is invoked. A function may carry several, and Cloudhopper generates each of them; the compatibility tests cover each trigger on its own, so prefer one trigger per function. Without a trigger it can only be invoked directly, as far as the target allows; the support matrix lists what each target offers.

@HttpTrigger​

Exposes the function through an HTTP API gateway.

AttributeDescription
methodHTTP method, e.g. "GET", "POST"
pathRoute, may contain path variables, e.g. /player/{id}
operationIdOperation id used in the generated OpenAPI document
summary / descriptionHuman-readable API metadata

@ScheduledTrigger​

Invokes the function on a cron schedule. Scheduled functions usually take no parameters and return void.

AttributeDefaultDescription
cron— (required)Cron expression, e.g. "0 0 * * *"
timezone"UTC"Timezone the schedule is evaluated in
@Function(name = "nightlyCleanup")
@ScheduledTrigger(cron = "0 0 * * *", timezone = "UTC")
public void cleanup() {
    // ...
}
TargetScheduleNotes
aws-terraformEventBridge ruleEvaluated in UTC
azure-terraformTimer triggerEvaluated in UTC
gcp-terraformCloud Scheduler jobEvaluates timezone
springboot-httpSpring @Scheduled in the service, and POST /schedules/<function name>Evaluates timezone; see below

On Spring Boot every running instance fires the schedule on its own. That is right for a single instance. When the service runs with several replicas, or on a platform that scales to zero, set cloudhopper.schedules.in-process=false and let an external scheduler call POST /schedules/<function name> instead, for example a Kubernetes CronJob or the platform's cron trigger. Set cloudhopper.schedules.endpoint=false to switch the endpoints off.

@EventTrigger​

Invokes the function once for each event from a queue or a storage bucket.

AttributeDefaultDescription
source— (required)EventSource.QUEUE or EventSource.STORAGE
name— (required)Name of the queue or bucket: 3 to 63 lowercase letters, digits and single hyphens, starting with a letter
createtruetrue creates the queue or bucket with the function; false connects to an existing one of that name

Delivery is at least once: when the function throws, the platform delivers the event again, so make the function tolerate duplicates. A parameter of type EventMetadata gives you the event id, source, time, delivery attempt and attributes; on invocations that are not events it is null.

Queues​

For EventSource.QUEUE, the message body is deserialized from JSON into the body parameter, just like an HTTP request body.

@Function(name = "orderReceived")
@EventTrigger(source = EventSource.QUEUE, name = "orders")
public void onOrder(Order order, EventMetadata meta) {
    // ...
}
TargetQueueNotes
aws-terraformSQS queueOne message per invocation; failed messages are reported individually and delivered again
azure-terraformStorage queue in the function app's storage accountMessages must be Base64-encoded; after five failed attempts a message moves to <name>-poison
gcp-terraformPub/Sub topic, delivered through EventarcRequires the Eventarc and Pub/Sub APIs in the project
springboot-httpPOST /events/<function name>, or a Kafka topicThe body is the message; optional ce-id, ce-source and ce-time headers (CloudEvents) fill the metadata. Answers 204, or an error status if the function throws. With spring-kafka and cloudhopper.events.broker=kafka, the function consumes the topic <name>; after five failed attempts a message moves to <name>.DLT, see Queues from Kafka

Storage buckets​

For EventSource.STORAGE, the function is invoked for every object created or overwritten in the bucket. Its body parameter, if it has one, must be a StorageEvent: bucket, key and size of the object. The function reads the content itself if it needs it, with the storage client of the platform.

@Function(name = "invoiceUploaded")
@EventTrigger(source = EventSource.STORAGE, name = "acme-invoices")
public void onUpload(StorageEvent event) {
    // event.getBucket(), event.getKey(), event.getSize()
}
TargetBucketNotes
aws-terraformS3 bucket with an event notificationThe bucket is named <cloudhopper_name_prefix><name>. S3 keeps one notification configuration per bucket: with create = false, it replaces the notifications the bucket already has
azure-terraformBlob container in the function app's storage accountEvent Grid puts the events on the storage queue <name>-events, which the function reads
gcp-terraformCloud Storage bucket in gcp_region, delivered through EventarcRequires two one-time IAM grants, see Storage triggers
springboot-httpPOST /events/<function name>The body is {"bucket": ..., "key": ..., "size": ...}; bucket defaults to the name in the annotation

Bucket names on AWS and GCP are global across all accounts, so choose one that nobody else uses, for example one starting with your company name. Terraform does not delete a bucket that still contains objects.

When a target does not support something​

Not every target supports every trigger or attribute. AWS and Azure ignore the timezone of a schedule, for example. When you compile for a target, Cloudhopper reports what that target ignores:

[WARNING] NightlyCleanup.java:[24,48] Attribute 'timezone' of @ScheduledTrigger is not supported by generator 'aws-terraform'; it is ignored for this target.
[WARNING] ReportMemoryFunction.java:[32,40] Attribute 'memory' of @Function is not supported by generator 'azure-terraform'; it is ignored for this target.

To fail the build instead, pass the processor option -Acloudhopper.strictFeatureCheck=true (a compilerArgs entry of the maven-compiler-plugin). Vendor extensions are never reported, since they are meant for one target. Maven shows these warnings only with showWarnings enabled, which is the default from maven-compiler-plugin 3.13.0 on and set in projects generated by the archetype.

Binding request data​

Declare exactly the parameters your method needs and annotate them. The processor deserializes and converts each value to the parameter's declared type before calling your method.

AnnotationBinds toNotes
@RequestBodyThe deserialized request bodyAt most one per method
@PathParam("id")A path template variableBlank value → the parameter name is used
@QueryParam("q")A query string parameterBlank value → the parameter name is used
@HeaderParam("X-Token")An HTTP request headerThe header name is required and matched case-insensitively

Because a blank value falls back to the parameter name, @PathParam Integer id binds the {id} path variable without repeating the name.

Path, query and header values can be bound as String, Integer, Long, Double or Boolean (or the primitive types); they are converted for you.

A parameter of type HandlerContext is recognized automatically — no annotation needed — and gives you invocation metadata (request id, remaining time, memory limit, and so on). The same holds for EventMetadata in event-triggered functions (see @EventTrigger). Any other unannotated parameter is treated as the request body.

@Function(name = "updatePlayer")
@HttpTrigger(method = "PUT", path = "/player/{id}")
public Player update(@RequestBody Player input,
                     @PathParam Integer id,
                     @QueryParam("dryRun") boolean dryRun,
                     HandlerContext context) {
    // ...
}

The method's return value becomes the response body; a void method produces no response payload.

Vendor extensions​

When you need a provider-specific setting that has no dedicated @Function attribute, attach it as an @Extension. Prefer the constants in ExtensionKeys over raw strings.

@Function(
    name = "hello",
    extensions = {
        @Extension(
            name = ExtensionKeys.Aws.Architecture.KEY,
            value = ExtensionKeys.Aws.Architecture.Values.ARM64)
    })
@HttpTrigger(method = "GET", path = "/hello/{name}")
public String hello(@PathParam String name) {
    return "hello " + name;
}

Only generators that declare support for a given extension key act on it; others ignore it.

What gets generated​

At build time the processor generates, per function:

  • a core <Class>_<method>_Handler that adapts your method to the runtime, plus a provider wrapper (e.g. an AWS Lambda entry point),
  • the infrastructure-as-code for the active generator (Terraform, OpenAPI, …),
  • metadata under META-INF/.

You never edit these — rerun the build and they are regenerated. See the Demo Project Guide for a full walk-through of the output, and the Deployment Config API for the annotation reference.
